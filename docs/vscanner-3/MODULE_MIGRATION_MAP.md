# V-Scanner 3.0 — Module Migration Map

**Stage 01 deliverable.** Source-grounded against the Stage 00 audit (repo head `518b652`, unchanged from audited tree `39e54f8` except the tracker doc). No production code is moved in Stage 01; this map is the contract that Stages 02–03 will follow.

Repo discrepancy check vs Stage 00 inventory: **none** — modules, sizes, entry points, and defects verified unchanged (re-ran `py_compile` on all modules: OK; Click command set: unchanged 7 commands).

**Import-graph review (ROADMAP Stage 01 criterion — verified 2026-10-18 via AST parse):** local module dependency edges are `adb_setup→tools_manager`, `auto_setup→tools_manager`, `dependency_checker→tools_manager`, `main→{adb_setup, auto_setup, dependency_checker, digital_forensics, report_generator, scanner, ui_styles}`, `report_generator→permissions`, `scanner→{permissions, report_generator, tools_manager}`, with `digital_forensics`, `permissions`, `setup`, `tools_manager`, `ui_styles` having no local deps. `tools_manager` is the fan-in hub (4 consumers) — consistent with the provisioning-extraction decision (SC-7). DFS cycle check: **no cycles**; the layering in ARCHITECTURE_DECISIONS §2.1 resolves the historical `main ⇄ scanner` tangle by making the legacy shim a one-directional consumer of services.

Notation for Migration method: `keep` (untouched), `wrap` (compat facade; behavior via new service), `extract` (move logic into new package), `split` (one module → multiple targets), `replace` (new implementation supersedes legacy), `deprecate` (stay until Stage 16 then delete with approval), `drop` (functionality intentionally not carried forward).

Android modules are listed in one summary row: unchanged, out of scope, **no** migration row needed.
